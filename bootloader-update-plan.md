# План: одна схема обновления головы на всех чипах (загрузчик копирует) и переход по сети

Составлен 2026-11-17 сессией RTOS-arch. Ничего из этого ещё не сделано, кроме отмеченного «готово».

## Цель

Одно обновление головы на трёх чипах, как уже работает ESP8266 NONOS (eboot) и Beken (загрузчик ставит образ из `download`):

1. Плата перезапускается без модулей (`/modules/off`) — область модулей свободна.
2. Новая голова (сжатая) пишется в область модулей, за текущей головой.
3. Голова оставляет загрузчику отметку «скопировать» и перезагружается.
4. Загрузчик видит отметку, распаковывает голову на место приложения, проверяет, снимает отметку, запускает.
5. Новая голова ставит модули из того же `.ota` (Apply).

Пропало питание в шаге 4 — отметка осталась, копирование начинается снова при следующем старте. Настройки и калибровку радио
обновление не трогает. Маршрут WebUI один на все чипы (`HEAD_ROUTES` в `install.mjs` сводится к одной строке).

## Этапы

### 1. ESP8266 RTOS: модули (без решений владельца — продолжение уже принятого)
- `arch/esp8266rtos/modules_esp8266rtos.cpp`: область модулей от конца головы до каталога; каталог — две копии в секторах
  `0xF8000`/`0xF9000`, как на NONOS (последние секторы раздела factory, под настройками).
- Метка сборки (`__build_id_start`): `scripts/module_head.py` правит скрипт линковщика SDK (`esp8266.project.ld`, как
  `sections.ld` у ESP32).
- Связка модулей: путь ESP32 в `scripts/module_link.py` (у SDK тот же формат скриптов линковщика, что у IDF), RAM модулей —
  куча (у SDK нет IRAM-хвоста NONOS: проверить свободную IRAM после сборки).
- Образы: начальный `.bin` (загрузчик + таблица + приложение одним файлом для провода), `.ota` (голова + пакеты), как у
  остальных чипов.

### 2. Шаг копирования в загрузчике — один код на ESP8266 RTOS и ESP32
- Загрузчик SDK ESP8266 и загрузчик IDF устроены одинаково (`bootloader_support`). ESP-IDF 5 позволяет подменить часть
  загрузчика своим компонентом (`bootloader_components`) без форка IDF; в SDK 3.4 такого нет — правка в нашем пакете SDK
  (форк ESP8266_RTOS_SDK с тегом, его же нужно опубликовать).
- Общий код шага копирования: прочитать отметку, распаковать gzip (как eboot: голова в `.ota` уже сжата), записать
  по секторам, сверить контрольную сумму из отметки, стереть отметку. Чип даёт только чтение/запись/стирание флеша.
- Сборка загрузчика: на ESP8266 сейчас пропускается (на Windows его конфигурация требует mconf) — собирать его своим
  шагом в `scripts/esp8266_rtos_sdk.py`.

### 3. ESP32 на ту же схему
- Новая раскладка без safeboot (или с ним — решение 1 ниже), один большой раздел приложения: голова + модули.
- Голова пишет отметку вместо переключения в safeboot; `HEAD_ROUTES` ESP32 = как у остальных.

### 4. Переход по сети (разово, без провода)
- **ESP8266 NONOS → RTOS:** образ-переходник (расширение `code/migration-app`) ставится обычным `/upgrade`, eboot кладёт его
  в 0x0. Переходник принимает из браузера образ RTOS (без URL), пишет в верх флеша, проверяет; последним шагом —
  загрузчик SDK в 0x0, таблица в 0x8000, приложение в 0x10000, перезагрузка. Настройки 250/251 не трогаются.
- **ESP32 safeboot → новая раскладка:** голова (или safeboot) пишет новый загрузчик (0x1000), таблицу и приложение, затем
  перезагрузка. Перенос раскладки по Wi-Fi уже делали 11-05 на 10.0.5.66.
- Опасное окно — запись начала флеша (меньше секунды): пропадёт питание — нужен провод. Поэтому весь новый образ сначала
  скачивается и проверяется, начало флеша стирается последним.

### 5. Проверка
- Лабораторные платы: 10.0.5.0 (ESP8266), 10.0.5.66 (ESP32), 10.0.5.139 (Beken — регресс). Обновление головы, выключение
  питания посреди копирования, переход по сети. Рабочие платы — только после этого и с отчётом.

## Решения владельца (спрашивать по одному)

3. Где отметка «скопировать»: в RTC-памяти (пропадает при выключении питания) или в своём секторе флеша (переживает)?
